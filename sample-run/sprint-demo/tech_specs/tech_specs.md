# FocusFlow — a minimalist Pomodoro focus timer (iOS, SwiftUI)

Build a small, polished, LOCAL-ONLY iOS app. No backend, no accounts, no network.
Keep scope tight enough to finish and compile inside a time-boxed sprint.

## Core (must-have)
- A single main timer screen: a large circular countdown, Start / Pause / Reset.
- Work / Short-break / Long-break modes with sensible default durations (25 / 5 / 15 min).
- Auto-advance: after a work session it moves to a break, and back, tracking the cycle count.
- A lightweight session history (date, mode, duration) persisted locally with SwiftData.
- A simple Settings screen to adjust the three durations and how many work sessions precede a long break.

## Feel
- Clean, calm, modern SwiftUI. Dark-mode friendly. Haptic tick on start/complete.
- No third-party packages. iOS 17+.

## Explicitly out of scope (V2)
- iCloud sync, widgets, notifications, sounds library, statistics charts.

**Codex (QA & Risk · Pragmatist) — Round 1**

I’m with the timestamp-based model, and I want to tighten one thing so this doesn’t get hand-wavy later: we should treat the timer as a tiny state machine with exactly one source of truth for the active interval, not as “UI state plus some timing helpers.” That means `phase`, `phaseStartedAt`, `phaseDuration`, `isPaused`, and `pauseStartedAt` if we truly need pause support, but nothing like a mutable “seconds remaining” that gets decremented every second. The QA win here is obvious: when the app resumes, we can recompute from `Date()` and immediately know whether we’re still in the same phase or we’ve crossed the finish line. I’d also keep the one-phase-only reconciliation rule exactly as Gemini phrased it, because that’s the one place this can quietly become buggy if someone “improves” it into a loop later. If the app has been backgrounded past multiple boundaries, we should advance one step, log one completion, and stop. That’s the simplest honest behavior and it’s testable.

Where I want to push harder is on history and persistence. Claude’s “append-only, only on natural completion” is the right call, but the data model needs to be explicit enough that we can prove history is truthful. I’d store one SwiftData `SessionEntry` with `completedAt`, `mode`, and `durationSeconds`, and maybe `plannedModeAfterCompletion` is not necessary because the mode itself already tells the story. What I would not persist is the live timer state unless we’re deliberately accepting the force-quit reset limitation as final. Since that’s already agreed, don’t overbuild recovery. The important QA angle is making sure we never write history on reset, on pause, or on a partial background. Only write when a phase genuinely finishes, including the single reconcile step on resume. That gives us a clean invariant: every row in history corresponds to one completed interval the user actually got through.

For the build split, I think the smallest sane lanes are: one person on timer state/reconciliation and ring UI, one on SwiftData/history, one on settings/form wiring plus app shell. But even if it’s one developer sprinting solo, the implementation order should still respect risk: first lock the state machine and completion logic, then persistence, then polish. The easiest place to get burned is not the ring drawing, it’s the boundary math around pause/resume and auto-advance. I’d want a couple of very targeted tests around that logic: completion exactly at zero, resume after backgrounding with a partial elapsed interval, resume after backgrounding with enough elapsed time to cross one boundary, and reset not logging anything. If we can’t simulate those deterministically, we’re guessing, and guessing is how timer apps become flaky.

One thing I’d actually disagree with a bit is treating the haptics as purely “start and complete” without specifying the execution point. They need to be fired from the state transition, not from the UI button handler, or else resume/reconcile paths will miss them. That’s a subtle but real bug: if a phase completes while the app is backgrounded and the user returns, we still want the complete haptic when the app catches up, but only once. So the transition handler should own it, not the tap action. If we keep that boundary clean, the rest of the app can stay boring, and boring is exactly what we want here.

Codex, I'm on board with the state-machine shape, but let me push on the one thing that actually bites users: what timestamp goes into `completedAt` when we hit the single reconciled transition on resume.

If `completedAt` is "now" — the moment the app happens to be reopened — then picture the actual user here: they start a work session at 9am, get pulled into a meeting, and don't touch their phone again until 8pm. When they open FocusFlow that evening, reconciliation fires, logs one completed work session, and the History list shows "Work session — 8:00 PM." That's just wrong from the user's point of view. Nothing happened at 8pm. The session that actually got "completed" (in the honest, timestamp-math sense we're using to justify auto-advance) finished at 9:25am. If History is supposed to be, as Claude put it, "a truthful record of what was actually stuck with," then the timestamp has to be `phaseStartedAt + phaseDuration`, not `Date()` at reconciliation time. Otherwise we're solving the ring's honesty problem while quietly introducing a new dishonesty in the log. This is a two-line fix in the reconciliation function, but it's exactly the kind of thing that looks fine in a demo (where background gaps are seconds, not hours) and only shows up as a bug report from a real user weeks later. I want us to lock it now so nobody "simplifies" it into `Date()` under time pressure.

Same logic extends to `durationSeconds` — you're right it should be the planned/configured duration, not measured wall-clock elapsed, and for the same reason: if a user leaves the phone locked for three hours mid-work-session, we do not want History claiming a 3-hour work session. Configured duration is the truth we're logging, wall-clock is just the trigger for advancing state.

On ownership of the transition/haptic logic — strongly agree with firing from the state transition, not the button handler, but I want to be concrete about where that code physically lives, because this is where "one clean boundary" turns into "three files each doing half of it" if we're not careful. I want exactly one `@Observable` `TimerEngine` class, instantiated once at the App root, injected via `.environment`, and it is the *only* thing that (a) computes remaining time, (b) decides phase transitions, (c) calls into SwiftData to insert a `SessionEntry`, and (d) fires haptics. Sheets for Settings and History are pure readers/writers of engine state — Settings mutates duration config on the engine, History just queries the SwiftData store, neither one owns any timer logic. This matters for performance too: the main ring view should be the only thing re-rendering every second. I'd drive the tick with a single `Timer.publish(every: 1, on: .main, in: .common)` that's invalidated the instant we pause or the scene goes to background — not left running to burn battery while the phone's in someone's pocket — and resumed only through the recompute-on-`scenePhase`-change path we already agreed on. No `TimelineView(.animation)` for this; that's built for continuous graphics, not a once-a-second countdown, and it'll redraw far more than we need.

That actually changes my read of your lane split, Codex. Splitting "settings/form wiring plus app shell" off from "timer state/reconciliation" is fine for who types the code, but the app shell — the root `App` struct, the environment injection, the `scenePhase` observer that calls `engine.reconcile()` — is not really a separate concern from the engine, it's the engine's only caller. If we let that get built independently, whoever's on shell/settings will end up guessing at the engine's public API and we'll get a mismatch at integration time. So: whoever leads locks the `TimerEngine`'s public surface first — its published state, `start()`, `pause()`, `resume()`, `reset()`, `reconcile()` — as basically a one-page contract before anyone forks off. After that, ring UI, settings form, and SwiftData/history genuinely can go in parallel against that contract, same three lanes you proposed, I just don't want the shell treated as free-standing plumbing — it's the thing that proves the engine's timestamp math is actually wired to `scenePhase`, which is the single riskiest piece of this whole build.

**Gemini (Backend / Systems Engineer · Systems Thinker) — Round 1**

I'm fully on board with Claude’s correction regarding the `completedAt` timestamp. If we’re selling a "truthful record," logging completion at the moment of app-resume is data corruption by definition. Regarding the lanes, Codex, you’re right that we shouldn't treat the shell as free-standing. I propose the engine owner must define the `TimerEngine` interface in a distinct contract file immediately—a simple protocol or public struct defining exactly what `reconcile()`, `pause()`, and `resume()` do—so the UI and persistence lanes have a concrete target to build against before they write a single line of business logic. That’s our integration insurance.

For the data model, let's keep the `SessionEntry` lean. I'd add `mode` as an enum (`work`, `shortBreak`, `longBreak`), `durationSeconds` as an integer (storing the *intended* duration, not the actual elapsed wall-clock time, to ensure we don't accidentally log a three-hour session), and `completedAt` as the precise timestamp of completion. Simple, flat, zero relationships. I’m also going to insist that the `TimerEngine` is the sole gatekeeper for SwiftData operations; nothing else touches the model context except the engine (which performs the writes) and the History view (which performs the reads). If we let the UI components or the App delegate start firing off context saves, we’ll end up with fragmented persistence logic that’s impossible to debug.

We also need to be explicit about testability for that reconciliation math. If we don't have a way to inject a "mock" date/time into the engine, we are going to be manually testing boundary conditions for the next three days. Let's make sure the engine's time-math is separated from the `Date()` call via a provider or just a simple initializer injection. If we can’t write a unit test that says "Given a start time of T-100 seconds and a duration of 60 seconds, expected state is completed," we’ve already failed the system design.

## Final Output

**State machine:** One source of truth, no ticking counter. `TimerEngine` is an `@Observable` class holding `phase` (`.work`/`.shortBreak`/`.longBreak`), `phaseStartedAt`, `phaseDuration`, `isPaused`, `pausedAt`, plus `completedWorkSessions` (cycle count) and the configured durations/sessions-before-long-break. Remaining time is always computed, never stored: `phaseDuration - Date().timeIntervalSince(phaseStartedAt)` (adjusted for pause time folded back in on resume). Instantiated once at the App root, injected via `.environment`. It's the sole owner of: computing remaining time, deciding phase transitions, writing to SwiftData, and firing haptics. Settings and History are pure readers/writers of engine state — no timer or persistence logic anywhere else.

**Public contract (write this file first, before any lane forks):**
```
start()      // begin current phase from now
pause()      // record pausedAt
resume()     // fold paused duration back into phaseStartedAt
reset()      // restart current phase at full duration; no log, no phase/cycle change
reconcile()  // called on appear + scenePhase → .active
```
`reconcile()` is capped at exactly one phase transition, no matter how long the app was backgrounded — if elapsed time crosses multiple boundaries, complete and log the current phase, advance one step, start the new phase's clock from now, and stop. This is a hard rule enforced by the implementation (guard against a while-loop), not just a convention.

**Timestamp fix (the one real correction this round):** When `reconcile()` detects a completed phase, log it with `completedAt = phaseStartedAt + phaseDuration` — the moment the phase actually finished — never `Date()` at resume time. Likewise `durationSeconds` in the log is always the configured/planned duration, never measured wall-clock elapsed. History reflects when things actually finished and how long they were meant to run, not when the user happened to reopen the app.

**Data model:** One flat SwiftData model, `SessionEntry`: `completedAt: Date`, `mode: Mode` (enum: work/shortBreak/longBreak), `durationSeconds: Int`. No relationships, no extra fields. Only `TimerEngine` touches the `ModelContext` for writes; `History` view only reads. Logged only on natural completion (including the single reconciled transition) — never on reset, pause, or plain backgrounding.

**Haptics:** Two patterns — phase start, phase completion — fired from inside the engine's transition logic (`start()`/`reconcile()`), never from button tap handlers directly, so a completion that happens during a background reconcile still fires the haptic exactly once when the app resumes.

**Testability:** The engine takes its time source as an injectable dependency (defaults to `Date()`, but overridable in tests) so reconciliation math can be unit tested deterministically: exact-zero completion, partial elapsed resume, multi-boundary resume (verifying single-step advance), and reset-logs-nothing.

**Timer tick:** Single `Timer.publish(every: 1, on: .main, in: .common)`, invalidated on pause and on background, restarted only through the `scenePhase`-triggered `reconcile()` path. No `TimelineView(.animation)`.

**Build lanes (engine contract ships first, then parallel):**
1. `TimerEngine` + reconciliation logic + ring UI (owns the app shell's `scenePhase` observer too — this is the engine's only caller, not a separate concern)
2. SwiftData `SessionEntry` + History sheet (read-only)
3. Settings sheet (Form + Steppers, mutates engine's duration config)

Lane 1 must land the engine's public surface (the five methods above) as a locked contract before 2 and 3 write code against it.
