What I found and fixed this round, purely in `ContentView.swift`: the Start/Pause button always called `engine.resume()`, even for the very first tap of a phase. `resume()` just folds elapsed pause-time back into the clock — it never re-reads `phaseDuration` from current settings and, more importantly, never fires `haptics.playPhaseStartHaptic()`. Only `start()` does that. Net effect: the "haptic on phase start" behavior we locked in during design never actually fired for a user pressing Start — only the natural-completion auto-advance path fired it. And if someone changed a duration in Settings before ever pressing Start (or right after a Reset), that new duration got silently dropped.

Fix: added a small `isFreshPhase` computed property (`engine.isPaused && remainingTime >= engine.phaseDuration` — true only when the phase hasn't progressed at all) and route the button through `engine.start()` in that case, `engine.resume()` otherwise. Didn't need any new engine API for this — everything's built from the public surface `TimerEngine` already exposes.

Also unified `reconcileWithTransition()` so the ticker's per-second tick uses it too, not just `onAppear`/`scenePhase` changes — so the soft scale-and-fade bounce now plays consistently whenever a phase naturally completes, whether the app was foregrounded the whole time or just resumed from background. One helper, no new mechanism.

Left for the integrator: `project.yml` doesn't yet set `CODE_SIGNING_ALLOWED`/`CODE_SIGN_STYLE`/`DEVELOPMENT_TEAM` per the real-device requirement, and there's no `Info.plist` at `Sources/App/Info.plist` yet even though `project.yml` points there — both are shared-config territory, not mine to touch.
