## Original Prompt

```
# FocusFlow — a minimalist Pomodoro focus timer (iOS, SwiftUI)

Build a small, polished, LOCAL-ONLY iOS app. No backend, no accounts, no network.
Keep scope tight enough to finish and compile inside a time-boxed sprint.

## Core (must-have)
- A single main timer screen: a large circular countdown, Start / Pause / Reset.
- Work / Short-break / Long-break modes with sensible default durations (25 / 5 / 15 min).
- Auto-advance: after a work session it moves to a break, and back, tracking the cycle count.
- A lightweight session history (date, mode, duration) persisted locally with SwiftData.
- A simple Settings screen to adjust the three durations and how many work sessions precede a long break.

## Feel
- Clean, calm, modern SwiftUI. Dark-mode friendly. Haptic tick on start/complete.
- No third-party packages. iOS 17+.

## Explicitly out of scope (V2)
- iCloud sync, widgets, notifications, sounds library, statistics charts.
```

## Phase Purpose

Decide the key screens, the primary user flow, and the handful of design principles that govern them. Only what's buildable within the time box.

### Round 1


**Codex (Frontend Engineer · Skeptic) — Round 1**

I’m aligned with the “one screen, sheets for everything else” direction, but I want to push harder on one point: the app should be state-driven from the absolute timestamp, not just as a background fix, but as the core model for the whole timer. That’s the cleanest way to make auto-advance, pause, resume, and app relaunch all consistent without inventing a bunch of fragile “seconds left” bookkeeping. If Claude’s suggestion was “we need a reliable background fix,” I’d say the real win is broader: the timer should always derive its displayed state from `phase`, `startDate`, `pauseDate` if needed, and `duration`. Then the UI is just a projection of truth, which is exactly what SwiftUI wants.

I also think we should be strict about the history rule: log only natural completions, not resets, not app resumes, not forced catch-up. That keeps the data honest and avoids a weird half-truth where the history implies the user completed sessions they abandoned. Same for the force-quit limitation: Gemini’s version is fine, but I’d make it explicit in design and copy that the app is intentionally not trying to reconstruct an interrupted session after kill. That sounds like a gap, but in a time-boxed sprint it’s the right trade-off because any attempt to “restore everything perfectly” would quietly expand into persistence edge cases, clock drift debates, and fake precision.

One place I’d resist overcomplicating: the primary navigation. No tabs, no stack, no separate timer/history/settings destinations. The timer screen should stay dominant and everything else should feel like secondary panels. If we let history or settings become full-screen destinations, we’ll lose the calm, glanceable feel and spend the sprint building navigation instead of the timer itself. So my vote is: keep the main screen as the only real screen, use a bottom sheet for settings/history, keep the data model simple, and make the timer logic timestamp-based from day one. That gives us the best chance of shipping something polished that doesn’t lie.

**Claude (Product Strategist · Pragmatist) — Round 1**

Codex's timestamp-as-source-of-truth model is the right call and I don't think it's even a debate — the alternative (mutable "seconds remaining" state you tick down every second) is exactly the kind of thing that looks fine in a demo and then falls apart the moment someone locks their phone mid-session, which is going to happen constantly since this is a *timer app people put in their pocket*. So yes, `phase + startDate + duration` (plus whatever minimal pause bookkeeping you need — an `elapsedBeforePause` or a `pausedAt` you fold back in on resume) as the single source of truth, UI as a pure projection. Agreed, moving on.

But I want to push on one thing Codex's framing glosses over, because it's a real product decision hiding inside what sounds like a purely technical one: what happens when elapsed time on resume is bigger than the *current* phase's remaining duration? Say I start a work session, background the app, and don't come back for three hours. If we're strict about "always recompute from the timestamp," the naive version cascades — work session ends, 5-min break starts and immediately ends, next work session starts and ends, etc., all the way until we land on whatever phase "would be active right now," logging every single one of those to history along the way. That's a disaster for the "history is a truthful record of what was actually stuck with" principle Codex just argued for two paragraphs earlier — you'd open the app after a lunch break and find eight fabricated completed sessions and a cycle count that jumped from 1 to 9. Nobody did that work.

So my proposed rule, and I think this is the actual design decision this phase needs to lock: reconciliation caps at **one** phase transition. If the current phase's time has elapsed, complete and log *that one phase*, advance to the next phase, but start the next phase's clock from "now," not from when the skipped phase mathematically would have ended. You never cascade through more than one auto-completion on resume. This keeps the "truthful history" promise intact, it's trivial to implement (it's just an `if elapsed >= duration`, not a `while` loop), and it matches how a human actually thinks about it — "oh, I missed my break, no big deal, back to work" — rather than the app hallucinating a productive afternoon. I'd bake this into the design principles list explicitly so nobody "cleans it up" into a while-loop later thinking they're being more correct.

Separately, on the product-value side: if the pitch from the last phase was "quiet coach, not a stopwatch," the one thing on the main screen that actually earns that framing — without turning into the statistics screen we explicitly ruled out — is a small "Work 2 of 4" style label near the ring showing progress toward the long break. That's not a new screen, not a chart, it's one Text view bound to state we already have (cycle count, sessions-before-long-break from Settings). Costs almost nothing, and it's the difference between "a countdown" and "a system that's tracking the rhythm for you," which was the whole point everyone agreed on. I'd resist going further than that one label though — no per-day summaries, no "you're on a streak," nothing that creeps toward stats. And on Settings: keep it to three duration steppers plus one integer stepper for sessions-before-long-break, default 4, no custom picker wheels, no presets UI — a Form with Stepper rows is genuinely enough and anything fancier is sprint time we don't have.

One more scope guardrail I want on record: the prompt says haptic on start/complete only. Not on pause, not on reset. Small thing, but "add a subtle haptic on reset too, it feels nice" is exactly the kind of unscoped polish that eats an hour for zero product value — I'd hold the line at literally what's specified.

**Gemini (Design Lead · User Advocate) — Round 1**

I love the technical consensus we've reached, but I want to make sure the user side of this "quiet coach" isn't getting lost in the machinery. Claude, your point about capping the reconciliation at exactly one phase transition is absolutely brilliant—it’s the difference between a tool that’s reliable and one that’s actively gaslighting the user after they come back from a long break. That principle needs to be a core design rule: we never, ever auto-advance more than once, no matter how long the app was in the background.

Codex, you're dead right on the navigation. If we even think about adding a tab bar or a navigation stack, we're building a different app, not this one. The home screen needs to be just the ring, and the settings and history should exist only as auxiliary sheets that slide up and slide away. That keeps the "one task at a time" mindset front-and-center. But regarding that "coach" feeling—let's make sure the auto-advance doesn't feel jarring. If the user comes back to the phone and the timer has silently moved from a work phase to a break, there needs to be a tiny, elegant way they notice that transition without being nagged. I’d propose a very soft, standard SwiftUI scale-and-fade animation on the timer ring the moment the app detects the completed work session on resume. It’s the digital equivalent of a coach gently tapping you on the shoulder to tell you it’s time to breathe.

As for the history, I agree with Codex on keeping it purely for natural completions. It’s the only way the user can actually trust the data as a record of their focus, not just a log of when they opened the app. And Claude, your warning on haptics is well-taken; we absolutely shouldn't creep into "it feels nice" territory there. Let's stick strictly to the start and end of phases, and I'd argue we should use two distinct, recognizable haptic patterns so the user doesn't even need to look at the screen to know whether they’re being told to start working or stop for a break. That’s the kind of polish that separates a utility from a true, quiet coach.

## Final Output

Everyone landed in the same place, so here's the locked design for this sprint.

**Screen structure:** One screen only — the circular timer fills the home screen, no tab bar, no navigation stack. Settings (gear icon) and History (list icon) are presented as sheets that slide up and away. Nothing gets promoted to a full destination.

**Timer state model:** Timestamp-based, not a ticking counter. State is `phase + startDate + duration`, plus minimal pause bookkeeping (a `pausedAt` folded back in on resume). The UI is a pure projection of that state — recomputed on appear and on `scenePhase` changes, never mutated tick-by-tick.

**Reconciliation on resume — capped at exactly one phase transition.** If the current phase has elapsed, complete and log that one phase, advance to the next, and start its clock from "now." Never cascade through multiple auto-completions no matter how long the app was backgrounded. This is a hard design rule, not an implementation detail — it's what keeps history truthful and stops someone from "cleaning it up" into a while-loop later.

**History:** Flat, reverse-chronological, one SwiftData model. Logged only on natural completion (including the single reconciled transition above). Resets, backgrounding, and force-quit relaunches log nothing. Force-quit mid-session resets to the start of the current phase on relaunch — an accepted, named limitation, not something we engineer around.

**Main-screen polish, kept intentionally small:**
- A one-line "Work 2 of 4" style label near the ring, bound to existing cycle-count + sessions-before-long-break state. This is the entire concession to "quiet coach" — no charts, no streaks, no per-day summaries.
- A soft, standard SwiftUI scale-and-fade on the ring when a resume detects a completed phase transition, so the jump doesn't feel jarring.
- Two distinct haptic patterns, fired only at phase start and phase completion — nothing on pause, nothing on reset. Hold this line strictly; it's explicitly scoped in the prompt and anything more is unscoped polish we don't have time for.

**Settings:** A plain `Form` with `Stepper` rows for the three durations plus one integer `Stepper` for sessions-before-long-break (default 4). No custom pickers, no presets UI.

**Reset:** Restarts only the current interval to full duration. Doesn't touch cycle count, doesn't change phase, logs nothing. No skip-forward control in this build — that's a known, deliberate gap for V2.

This carries forward as the spec for the next phase to build against.
