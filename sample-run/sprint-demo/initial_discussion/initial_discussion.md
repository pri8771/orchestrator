```
# FocusFlow — a minimalist Pomodoro focus timer (iOS, SwiftUI)

Build a small, polished, LOCAL-ONLY iOS app. No backend, no accounts, no network.
Keep scope tight enough to finish and compile inside a time-boxed sprint.

## Core (must-have)
- A single main timer screen: a large circular countdown, Start / Pause / Reset.
- Work / Short-break / Long-break modes with sensible default durations (25 / 5 / 15 min).
- Auto-advance: after a work session it moves to a break, and back, tracking the cycle count.
- A lightweight session history (date, mode, duration) persisted locally with SwiftData.
- A simple Settings screen to adjust the three durations and how many work sessions precede a long break.

## Feel
- Clean, calm, modern SwiftUI. Dark-mode friendly. Haptic tick on start/complete.
- No third-party packages. iOS 17+.

## Explicitly out of scope (V2)
- iCloud sync, widgets, notifications, sounds library, statistics charts.
```

### Round 1


**Codex (Product Strategist · Visionary) — Round 1**

I think the sharpest version of this is not “a timer app with a few settings.” It’s “the fastest path from distracted to back on track.” That means the product has to feel almost invisible until the moment you need it, then give you one job: start a focus block, trust the system, and stop thinking about setup. For that reason I’d keep the core screen brutally simple: the ring, the mode, one primary action, and a very clear next-state preview. The history is worth keeping only if it answers a real question like “did I actually stick with this today?” If it turns into a stats graveyard, it’s dead weight for a sprint app.

I’d push hard on the auto-advance and cycle logic as the real product value, not just a nice-to-have. That’s what makes it feel like a coach instead of a stopwatch. The app should quietly manage work, short break, and long break transitions without making the user do math. If we’re only building one “remarkable” thing beyond the usual Pomodoro clone, it should be the sense that the app is guiding a rhythm, not just counting down minutes. Haptics on start and completion help that a lot because they make the experience feel tactile and deliberate without needing notifications or audio complexity.

Where I’d be strict is scope. Settings are in, but only for the few things that change the rhythm: three durations and the long-break interval. No custom labels, no themes, no charts, no account, no sync, no widgets. Session history stays local and tiny: date, mode, duration, maybe completion status if that’s cheap, but not analytics. For a <1-hour build, the must-haves are just enough to support daily use: timer control, mode progression, local persistence, and duration settings. Anything else is decoration and will dilute the sprint.

If we want this to feel genuinely good rather than merely functional, the success bar is simple: a user can open the app, start a work session in under 2 seconds, get through a full work/break cycle without confusion, and later glance at history to confirm they actually used it. If it does those four things cleanly, it’s a strong MVP. If we start chasing more, we’ll end up with a mediocre app that does too much instead of a tight one that feels confident.

**Claude (Design Lead · Skeptic) — Round 1**

Codex, I like the "coach, not stopwatch" framing, but I want to push back on one thing before we build on it: you said history is "worth keeping only if it answers a real question" and hinted it could be cut if it turns into a graveway. It's not actually optional — the spec says "persisted locally with SwiftData" as a must-have, full stop. So the question isn't whether we keep it, it's how thin we can make it so it doesn't eat sprint time. My answer: a flat reverse-chronological list, no grouping by day, no charts, no swipe-to-delete even — just rows of "Work · 25 min · 2:14 PM" appended as sessions complete. One SwiftData model, one List view, done in ten minutes. If we start debating streaks or daily totals we've already lost the plot.

Now let me be the skeptic on the thing everyone's excited about — auto-advance and the cycle count. That's the "coach" feeling, sure, but it's also the single most likely place this app silently breaks, and nobody's mentioned it yet. If we implement the countdown as a plain decrementing Timer/state variable, the second the user backgrounds the app — switches to Messages, takes a call, whatever — iOS suspends that timer. There's no notifications in scope, so there's no way to alert them a session ended. When they come back, if we've been naively ticking down a stored "secondsRemaining" int, either it's frozen (wrong) or it's fine because iOS paused it too (also wrong, because now a 25-minute work session that actually took them 40 minutes of wall-clock time reads as "still going, 3 minutes left"). The only correct approach is to store an absolute start timestamp + target duration and always compute remaining time as `target - Date().timeIntervalSince(start)` recalculated on `.onAppear`/`scenePhase` changes. That's a design decision as much as an engineering one, because it affects what the user sees the instant they reopen the app after being away: if the session actually elapsed while they were gone, we should show it as already complete and already auto-advanced to the next mode, not have them watch a countdown "catch up." That's the difference between feeling like a coach and feeling broken.

Same root issue applies to cold launch / app kill, which I haven't heard anyone raise: if the user force-quits mid-session (very normal iOS behavior, people do this constantly), does the timer just reset to 25:00 when they reopen, silently lying about progress? For a sprint build I'd say we accept that as a known limitation rather than build persistence-of-in-progress-state on top of everything else — but we should say that out loud now, not discover it during a demo. What I do think we must nail down, because it's cheap and it's a real ambiguity: what exactly gets written to history. My vote is only on natural completion — i.e., when a mode's timer hits zero and auto-advance fires, log the just-finished interval. Hitting Reset should NOT log anything, because reset means "this didn't happen," and if we log resets too the history becomes noise instead of a truthful record of what you stuck with — which, going back to Codex's own success bar of "glance at history to confirm I actually used it," is the whole point of the feature. That also cleanly answers whether breaks get logged: yes, every mode gets logged on completion including breaks, since the model field is literally `mode`, and it costs us nothing extra.

On layout: I'd resist a tab bar. This is a one-screen app pretending otherwise would be scope creep in the wrong direction — the main timer view is the whole app, with a gear icon in the top-right for Settings and a small clock/list icon in the top-left for History, both presented as sheets. That keeps the "open app, hit start in under 2 seconds" promise Codex wants, because the ring is the very first and only thing you see, full stop — no home screen, no tab switching. Last thing I want us to lock down explicitly before anyone writes code: Reset only resets the current interval back to its full duration and does not touch the cycle count or jump you to a different mode — there's no skip button in this build. I know that means if someone's mid-break and wants to bail straight to work, they're stuck watching it or resetting the break (which just restarts the break, not skip it). That's a real gap, but adding a "skip forward" affordance is exactly the kind of extra control-surface decision that eats sprint time for a case that's genuinely V2. I'd rather ship the honest, narrow version and name the limitation than half-build a skip feature and leave its edge cases (does skipping still count toward the cycle? does it log to history?) unresolved when time runs out.

**Gemini (QA & Risk · Pragmatist) — Round 1**

Claude, you're spot on about the backgrounding. If we don't store the absolute target end-time and recalculate on `.onAppear`, we aren't building a timer, we're building a source of frustration. The user comes back, sees it's stuck at 00:00 because the app was suspended, and they'll instantly distrust it. That's non-negotiable for me. If we're going to build this as a coach, it needs to handle the reality of an iOS lifecycle, and recalculating against `Date()` is the only way to do that safely without building a complex notification-driven system which we clearly don't have time for.

Codex, I love the "coach" framing, but as the QA guy, I'm already worrying about "state drift" if we try to be too clever with auto-advancing across app lifecycle changes. I think we need to define the reset behavior strictly. If I'm halfway through a break and I force-quit, does the app assume I finished it? If we want a reliable coach, it should be conservative. If you kill the app, we reset to the start of the current mode on relaunch. That's honest, it's safe, and it avoids us having to write complex "what did I miss?" reconciliation logic in 45 minutes.

Also, regarding history, let's stick to Claude's plan: append-only on successful completion. If we try to allow deletion or fixing history, we're in app settings hell. Let's just output a simple text entry into SwiftData when the timer hits zero. That's it. If it's not a completed session, it never touched the database. That keeps our data model dead simple and our codebase lean.

One last thing: no tab bar is correct. Let's make sure the entry point—the Timer—is instantly ready. I’d even argue for not even having a navigation stack at the root. Just the main timer view. The history and settings are purely auxiliary. If we want this to feel like a modern iOS app, the circular timer needs to animate smoothly—but let’s keep the animations standard SwiftUI primitives. Custom Bezier paths will just be another thing to debug when we're 5 minutes from the deadline.

## Final Output

Everyone converged on the same shape for this app, with no real fights left standing.

**What it is:** Not just a Pomodoro clone — the goal is to feel like a quiet coach that manages the work/break rhythm for you, not a stopwatch you have to babysit. Open the app, hit Start in under 2 seconds, and trust it to auto-advance through work → break → work and track the cycle count.

**Screen structure:** One screen, no tab bar, no nav stack. The circular timer is the entire home screen. Settings (gear icon) and History (list icon) are auxiliary — presented as sheets, not separate tabs — so the ring is always the very first thing you see.

**The backgrounding/timer-accuracy fix (this was the key technical risk raised, and everyone agreed on the same fix):** Don't decrement a stored "seconds remaining" counter. Instead store an absolute start timestamp + target duration, and always recompute remaining time as `target - Date().timeIntervalSince(start)` on appear / scenePhase changes. This means if the user backgrounds the app and comes back after the session would've ended, the app correctly shows it as already complete and already auto-advanced — not a countdown frozen or "catching up."

**Force-quit / app-kill behavior:** Treated as an accepted, named limitation rather than something to engineer around. If the user force-quits mid-session, the app resets to the start of the current mode on relaunch — no attempt at reconciling "what did I miss," no persisted in-progress state. Simple and honest, not silently lying about progress.

**History:** Flat, reverse-chronological list, one SwiftData model, no grouping/charts/streaks/delete. Append-only, and only on **natural completion** (timer hits zero and auto-advances) — hitting Reset logs nothing, since the point of history is to be a truthful record of what was actually stuck with. Every mode (work, short break, long break) gets logged the same way.

**Reset behavior, locked down:** Reset only restarts the *current* interval back to full duration — it does not touch the cycle count and does not jump to a different mode. There's no skip-forward button in this build; that's explicitly called out as a real gap but intentionally left for V2 rather than half-building it.

**Polish guardrails:** Standard SwiftUI animation primitives for the ring — no custom Bezier paths, to avoid last-minute debugging risk.

No open disagreements remain — Gemini's "reset to start of current mode on force-quit" was just making concrete what Claude had already flagged as an accepted limitation, not a contested point.
